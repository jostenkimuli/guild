Auth, Roles & RLS

Authentication via Supabase Auth, authorization via platform roles + per-space roles, and row-level security as the enforcement boundary.

Authentication flow

  • Email/password sign-in and sign-up through the /login client form.
  • Session cookies are kept fresh by the proxy on every request (see Architecture).
  • Browser components use @/lib/supabase/client; server pages/actions use @/lib/supabase/server.
  • Admin-created accounts sign in with a temporary password and are forced to /setup-password (must_change_password) before use.
  • New public signups trigger on_auth_user_created → a profiles row.

Approval states

  • pending — created but not yet approved; consoles show an “awaiting approval” state.
  • approved — cleared to act at the platform level.
  • Ecosystem admins created by the super admin are auto-approved (migration 20260829000001); those created by a program admin start pending.

The RLS model

RLS is the security boundary. The pattern every table follows:

-- every row on the platform resolves to a Space ...
CREATE POLICY "..._members_read" ON ... FOR SELECT USING (
  space_id IN (SELECT space_id FROM space_memberships WHERE user_id = auth.uid())
);
CREATE POLICY "..._staff_write" ON ... FOR ALL USING (
  EXISTS (SELECT 1 FROM space_memberships
          WHERE space_id = ... AND user_id = auth.uid()
          AND role IN ('admin', 'teacher'))
);
-- ... scoped through the Space's membership model
  • Members read; space staff (admin/teacher) write — scoped through the curriculum’s Space.
  • Self-joins (learners joining spaces) are limited to learner/collaborator roles.
  • Teachers/mentors/admins are assigned only by space staff.
  • Ecosystem/space ownership is enforced through created_by and the ecosystem_staff link.
  • SECURITY DEFINER helpers resolve any curriculum row to its space so deep rows (topics, lessons, activities) inherit the same scoping.
  • Ecosystem visibility policies evaluate row-native columns (PG17-safe for INSERT/UPDATE…RETURNING) — migration 20260902000001.

Delegated approval

Ecosystem-admin approvals always start with the super admin. The super admin can either approve directly or delegate that authority to a program admin by setting profiles.can_approve_ecosystem_admins = true (setProgramAdminDelegation). A delegated program admin then sees and approves pending ecosystem admins from the program console.

Invitation codes

  1. Space admin generates a code with a role (learner, teacher,…), optional maximum uses, expiry, and optional grade link.
  2. The public /login sign-up flow collects the code (invitation_code_info RPC validates it).
  3. Signup redeems the code and adds the subscriber as a space_memberships row with the code’s role.

Seeded example: MATHLAB → learner in Primary Mathematics Space (max 50 uses).

Locked profile columns

A trigger locks profiles.role, status and can_approve_ecosystem_admins so ordinary users can’t escalate themselves. The super admin may change any of them; a delegated program admin may only touch ecosystem-admin status.

Security checklist

  • Every new table: RLS enabled + explicit GRANTs + row-level policies.
  • Verified with positive and negative tests (a member can read; a non-member cannot; a learner cannot write).
  • Service-role key is server-only and never in client bundles.
  • No secrets in code or repository; .env.local git-ignored.
  • Regenerate + commit database.types.ts after schema work.
