Rendering & component model

  • Server components are the default. All pages and layouts fetch data server-side; the "use client" directive is reserved for pieces that need browser behavior (forms, dialogs, toasts).
  • params / searchParams are Promises in this Next.js version — always await them in page components.
  • Middleware was renamed to proxy in Next 16; the module lives at src/proxy.ts.
  • Server data reads happen in page/layout components or server actions; there are no legacy API routes for the core flows.

The proxy

Next.js 16 renamed middleware to proxy. src/proxy.ts runs on every non-static request (static assets, images and favicon are excluded). It performs three jobs:

1. Session refresh

A Supabase server client is created that reads and writes cookies, ensuring cookies stay fresh. This lives in the proxy rather than per-page so the session never goes stale.

2. Ecosystem subdomain rewriting

When a request arrives on a subdomain such as school.localhost, the proxy extracts the ecosystem slug and rewrites paths:

Requested pathRewritten to
//ecosystem/[slug]
/spaces/ecosystem/[slug]/spaces
/staff, /members, /students/ecosystem/[slug]/<segment>
Anything else (/login, /s/...)Resolved normally under the subdomain

3. Auth guard redirects

  • Unauthenticated users hitting /admin, /ecosystem, /spaces or /setup-password → redirected to /login.
  • Authenticated users on /login → redirected to the role-appropriate page (/admin for super/program admin, /ecosystem for ecosystem admin, / otherwise).

Ecosystem subdomains

Each ecosystem gets a slug-driven subdomain, expressing the product goal of “every ecosystem has its own front door”.

  • NEXT_PUBLIC_APP_HOST (default localhost) is the base host; lib/subdomain.ts exposes ecosystemSlugFromHost().
  • next.config.ts allows *.localhost dev origins so subdomains work under Turbopack.
  • Public profile pages live at /s/[slug] and are reachable regardless of subdomain.

Conventions to follow

  • Server components by default; add "use client" only where interactivity demands it.
  • Always await params / searchParams.
  • Data access goes through the typed Supabase clients — never raw SQL from app code.
  • Every schema change is a migration with RLS + explicit grants (see Database).
  • Use shadcn/ui components; don’t hand-roll duplicates.
  • No secrets in code or repository.
