Server Actions

All data writes flow through server actions in src/app/actions/. They run with full server privileges, validate input, and call Supabase on behalf of the signed-in user with the service-role / anon key as appropriate.

On this page
The action pattern auth.ts — session console.ts — onboarding & governance curriculum.ts — blueprint wizard syllabus.ts — teaching plan lessons.ts — lesson delivery cycle

The action pattern

Each action module follows the same shape:

"use server";

export async function someAction(...) {
  const supabase = await createClient();   // server client (awaits cookies())
  // 1. read the current profile                        → getProfile()
  // 2. authorize (role / ownership checks)
  // 3. validate inputs
  // 4. mutate via supabase (with .select().single() etc.)
  // 5. revalidate cache + redirect / return result
}

Client forms call these via the form action attribute (progressive enhancement) and surface error/success through useActionState in components like <Feedback />.

console.ts — onboarding & governance

The largest action file (600+ lines). Handles the whole admin onboarding chain and space governance.

FunctionWhoPurpose
createProgramAdminSuper adminCreate a program admin account (starts pending).
approveProgramAdminSuper adminApprove a pending program admin.
setProgramAdminDelegationSuper adminGrant / revoke can_approve_ecosystem_admins on a program admin.
createEcosystemAdminProgram / super adminCreate an ecosystem-admin account (pending; super-admin-created ones are auto-approved via migration).
approveEcosystemAdminSuper admin or delegated program adminApprove a pending ecosystem admin.
createEcosystemEcosystem adminCreate their ecosystem, including school metadata (vision, mission, director, headteacher, location).
createSpaceAdminEcosystem adminCreate a space-admin account (auto-approved).
createSpaceSpace adminCreate a space (department / innovation_hub / project_group).
createInvitationCodeSpace adminGenerate an invitation code with role, optional grade link, max uses and expiry.
editSpaceSpace adminSubmit a space edit request (pending ecosystem-admin approval).
approveSpaceEditEcosystem adminApprove a pending space edit request — applies the changes.
rejectSpaceEditEcosystem adminReject a pending space edit request.

Internal helpers: getProfile(), isApprovedEcosystemAdminOfSpace(), validateAccountFields(), slugify(), generateCode().

Space edit workflow
Space edits are intentionally two-phase: the space admin proposes (space_edits record, status pending), the ecosystem admin approves or rejects. Nothing mutates spaces until approval.

curriculum.ts — blueprint wizard

FunctionPurpose
saveCurriculumDataBlueprint wizard action: creates or updates a whole curriculum tree (goals, grades, terms, units, topics) and optionally publishes it.

Called by the 6-step CurriculumDialog wizard (details → goals → grades → terms → units → topics). Re-running it upserts a shared structure across the selected grades.

syllabus.ts — teaching plan

FunctionPurpose
createSyllabusStaff (admin/teacher) or ecosystem admin: create or update a syllabus (upsert on curriculum_id) with grading policy, required materials, office hours and classroom expectations.

lessons.ts — lesson delivery cycle

Server actions for the lesson delivery cycle — used from /spaces/[slug] (curriculum library) and /spaces/[slug]/lessons/[id] (view + objective progress):

  • Publishing lessons (draft → ready → delivered) with pages, activities, assessments.
  • Recording objective status per session+objective+learner (not_attempted / developing / achieved / mastered).
  • Learner self-tracking on objective results.

Where to add a new action

  • Onboarding / governance → actions/console.ts
  • Curriculum / blueprint → actions/curriculum.ts
  • Teaching plan → actions/syllabus.ts
  • Lesson delivery → actions/lessons.ts
