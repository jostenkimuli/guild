Core entities

EntityWhat it isExample
EcosystemThe highest-level boundary (a university, a corporation, an alliance of countries). Hosts Spaces and Users.A sample primary school
UserAny individual on the platform; roles are fluid and per-space.Teacher, Learner, Mentor, Industry Partner
SpaceA sub-community within an Ecosystem where specific engagement happens.Physics Class, Regional Hackathon Group
ContentEducational materials used for teaching and learning (courses, videos, documents).A fractions video, a worksheet
ChallengeA problem statement posted by an entity seeking solutions.“Reduce school food waste” (Sprint 5)
ProjectA collaborative solution built by users in response to a Challenge.Market-stall pricing model (Sprint 6)

Core relationships

  • Ecosystems host multiple Spaces and Users.
  • Teachers publish Content inside a Space.
  • Mentors guide Learners through Projects or Content.
  • Users form teams to collaborate on Projects.
  • Projects are submitted to solve specific Challenges.

Structural constraints

  • A Challenge can be public to the whole Ecosystem or restricted to specific Spaces.
  • A User can be a Teacher in one Space and a Learner or Collaborator in another — roles are per-space, never global.
  • A Project must map directly to at least one Challenge to qualify for problem-solving tracks.
  • One ecosystem per creator: ecosystems_one_per_creator.

The curriculum tree (Sprint 2)

A Space hosts one or more curricula. Each curriculum is a tree that every row resolves up to; row-level security then scopes access through the Space: 

spaces
  └─ curricula  (+ curriculum_goals, curriculum_evaluations)
       └─ grades
            └─ terms
                 └─ units
                      └─ topics
                           ├─ learning_objectives
                           ├─ content
                           ├─ lessons
                           │    ├─ activities
                           │    ├─ assessments
                           │    └─ lesson_resources ──► resources (shared M2M)
                           └─ teaching_guidance
      (units may also carry projects)
PiecePurpose
CurriculumBelongs to exactly one Space; carries name, year, publish state and the curriculum goals it aims to achieve.
Grades → Terms → Units → TopicsThe academic tree a curriculum is taught through.
TopicWhat gets taught: ordering via sequence_order, duration_weeks, description.
Learning objectivesOrdered objectives for a topic (with success criteria in the delivery cycle).
Content / Teaching guidanceTopic-level materials for learners and teacher guidance respectively.
LessonsPlan with title, duration, delivery type (self_paced/live/hybrid) and publish state; linked to a topic and optionally a teacher.
Lesson pages / activities / assessmentsOrdered building blocks of a lesson (multi-page content, steps, quiz/exercise/test/project).
ResourcesShared library (link/video/document/text) linked to lessons many-to-many.
Projects (per unit)Unit-level projects for learners.
Curriculum evaluationsPeriod + achievement rate per curriculum.
SyllabiPer-curriculum teaching plan: grading policy, required materials, office hours, classroom expectations.

Every row resolves to its curriculum through SECURITY DEFINER helpers; RLS then scopes members-read / space-staff-write through the Space. See Auth, Roles & RLS.

Approval chain (Sprint 1)

super_admin ──creates──► program_admin (pending)
  └─ approves program admins
  └─ approves ecosystem admins
        └─ OR delegates approval to a program admin  (can_approve_ecosystem_admins)

program_admin ──creates──► ecosystem_admin (pending)

ecosystem_admin ──creates──► ecosystem (auto-staffed)
  └─ creates space admins (auto-approved)

space_admin ──creates──► spaces + invitation codes
  └─ signup with a code adds the subscriber as a member with the code's role

Ecosystem-admin approvals always start with the super admin, who can approve directly or delegate that authority to a program admin.
